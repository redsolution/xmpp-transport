# Сравнение логики MAX с `xmpp-transport-max`

Дата проверки: 2026-10-21. Это статический обзор текущего кода, без проверки на живом MAX и Xabber Server. Цель — найти изменения поведения при переносе, а не формальные различия в устройстве классов.

Проекты:

- Новый: `/home/ilya.basyrov/Projects/xmpp-transport`
- Исходный: `/home/ilya.basyrov/Projects/xmpp-transport-max`

Низкоуровневый MAX WebSocket-клиент перенесён почти без изменений. Основные риски сосредоточены в замене старых `Transport` и `SessionManager` общей логикой. При первоначальном обзоре 59 тестов `test_max_backend.py`, `test_xmpp_gateway.py`, `test_xmpp_groups.py` и `test_authentication.py` проходили, но описанные ниже сочетания условий в основном не проверяли.

## 1. Группы из snapshot проходят как прямые контакты — исправлено

**Старое поведение.** `_dispatch_snapshot_contacts()` исключал `chat.is_group` из обхода прямых чатов.

**Поведение до исправления.** Обход исключал только ID из адресной книги. Для остальных чатов создавался новый `MaxChat` без `is_group` и `members`; `is_group` по умолчанию равен `False`. Затем `_receive_chat()` публиковал `ContactChanged`, а не `ConversationChanged`.

**Последствие прежнего поведения.** Группа из snapshot могла появиться в ростере как `chat-<group_id>@max…`, а синхронизация настоящей Xabber-группы не происходила по этой ветке. Такой контакт мог остаться и после последующего создания группы.

**Исправление.** При синхронизации прямых контактов группы из snapshot пропускаются, как в исходном `xmpp-transport-max`. Контакты адресной книги и прямые чаты по-прежнему передаются обработчику.

**Код:** новый `xmpp_transport/adapters/backends/max/client.py:1942`, `models.py:61`, `plugin.py:540`; старый `xmpp_transport_max/max/backend.py:1938`.

**Проверка:** тест подаёт группу, прямой чат и контакт адресной книги; обработчику передаются только прямой чат и контакт.

## 2. Рабочая сессия запускается до закрытия QR WebSocket — исправлено

**Старое поведение.** После получения credentials `_finish_login()` закрывал QR-поток до `_activate()`. В коде есть объяснение: MAX может отклонить второй сокет только что авторизованного web-устройства.

**Поведение до исправления.** `AuthenticationCoordinator.respond()` сохранял credentials, останавливал старую сессию и запускал новую; `flow.close()` вызывался после `sessions.start()`.

**Последствие прежнего поведения.** QR мог быть принят, но рабочая сессия не поднималась из-за одновременно открытого QR-соединения. Credentials уже были сохранены, так что пользователь видел состояние, похожее на частично завершённый вход.

**Исправление.** После сохранения credentials и сверки старых привязок QR-поток закрывается до остановки и запуска рабочей сессии. Порядок остальных шагов авторизации сохранён.

**Код:** новый `xmpp_transport/application/authentication.py:105`; старый `xmpp_transport_max/core/session_manager.py:340`.

**Проверка:** тесты обычного входа и 2FA требуют закрытого QR-клиента до запуска рабочей сессии.

## 3. Не сохраняется исключительное владение MAX-аккаунтом — исправлено

**Старое поведение.** `save_session()` возвращал прежнего XMPP-владельца того же MAX-аккаунта. Транспорт закрывал его backend и посылал уведомление о переносе привязки.

**Поведение до исправления.** `save_encrypted_credentials()` обновлял только зашифрованные credentials и статус. В схеме были `remote_account_key` и уникальный индекс для активных привязок, но поле не записывалось.

**Последствие прежнего поведения.** Один личный MAX-аккаунт мог остаться активным у нескольких XMPP-пользователей. Уникальный индекс не защищал строки с `NULL` в `remote_account_key`.

**Исправление.** После MAX-авторизации вычисляется устойчивый HMAC-ключ аккаунта. В одной транзакции прежние привязки этого аккаунта отключаются, их credentials удаляются, а новая привязка активируется с ключом. Прежние записи без ключа сверяются по расшифрованным credentials. Живые сессии прежних владельцев закрываются, им отправляется уведомление. Для других backend сохранение credentials не меняется.

**Код:** новый `xmpp_transport/application/authentication.py`, `xmpp_transport/adapters/postgres/repositories.py`, `xmpp_transport/adapters/security/fernet.py`; старый `xmpp_transport_max/core/session_manager.py:354`.

**Проверка:** тесты проверяют транзакционное отключение прежней привязки, включая запись без ключа, закрытие прежней сессии и уведомление; реальную работу с PostgreSQL и XMPP отдельно не проверяли.

## 4. Ошибка одной сохранённой сессии способна остановить весь процесс — исправлено

**Старое поведение.** `SessionManager.start()` обрабатывал ошибку каждого пользователя отдельно, записывал статус и продолжал восстановление остальных.

**Поведение до исправления.** `SessionSupervisor.restore()` собирал ошибки и выбрасывал `SessionLifecycleError` для случаев вне узкого набора повторных попыток. Исключение поднималось из `ApplicationRuntime.start()` и останавливало запуск процесса.

**Исправление.** Для MAX ошибка отдельного binding записывается в журнал только как ID привязки и тип исключения; остальные привязки продолжают восстановление. Неудачная привязка остаётся активной для следующей попытки восстановления. Для других backend прежняя обработка ошибок сохранена.

**Код:** новый `xmpp_transport/application/session_supervisor.py:142`, `xmpp_transport/runtime/lifecycle.py:96`; старый `xmpp_transport_max/core/session_manager.py:169`.

**Проверка:** тест с двумя binding подтверждает, что один сбой не мешает другому, текст ошибки не попадает в журнал, а повторное восстановление может запустить неудачную привязку без повторного открытия здоровой сессии.

## 5. Убрана загрузка полного состава групп перед синхронизацией — средний–высокий риск

**Старое поведение.** `handle_max_chat()` вызывал `_full_group_chat_for_sync()`, который загружал полный список участников и при ошибке пытался обогатить имена по контактам. При обработке входящих сообщений также обновлял группу при запасных именах участников.

**Новое поведение.** `_receive_chat()` и `_receive_message()` публикуют группу по доступному `MaxChat`. В новом `MaxBackendSession` нет вызовов существующих методов клиента `fetch_full_group_chat()` и `enrich_group_member_contacts()`.

**Последствие.** Частичный snapshot может привести к отсутствующим участникам и именам вида `MAX user <id>` в Xabber-группе.

**Код:** новый `xmpp_transport/adapters/backends/max/plugin.py:540`; старый `xmpp_transport_max/core/transport.py:239`, `xmpp_transport_max/core/transport.py:645`, `xmpp_transport_max/core/transport.py:886`.

**Проверка:** snapshot с неполным списком участников и fallback-именами, затем ответ API с полным списком; сравнить создаваемые IQ и отображаемых участников.

## 6. Потеряно сопоставление ID групповых сообщений после рассылки Xabber — средний риск

**Старое поведение.** Транспорт запоминал дополнительные ID из возвращённой Xabber-копии сообщения, связывал их с MAX ID, мог кратко ждать обновлённую копию и разбирать ответ по цитате, если явного ID не было.

**Новое поведение.** `XmppDirectMessageGateway` игнорирует копию рассылки. `MessageRouter` сопоставляет ответ только с сохранёнными исходными client ID. Дополнительные stanza ID от Xabber и часть цитатных fallback-сценариев не используются.

**Последствие.** Ответ на сообщение группы, ссылающийся на ID копии Xabber, может уйти в MAX с неверным `reply_to_message_id` либо как обычный текст.

**Код:** новый `xmpp_transport/adapters/xmpp/gateway.py:107`, `xmpp_transport/application/message_router.py:106`; старый `xmpp_transport_max/core/transport.py:1251`, `xmpp_transport_max/core/transport.py:1304`.

**Проверка:** отправить групповое сообщение, получить копию с иным stanza ID, затем ответить на неё из клиента Xabber; проверить MAX `message.link.messageId`.

## 7. Не обрабатываются подписки на виртуальные контакты — средний риск

**Старое поведение.** Компонент слушал `subscribe`, `subscribed`, `unsubscribe`, `unsubscribed`. Транспорт подтверждал подписку и при удалении контакта сбрасывал синхронизационную подпись.

**Новое поведение.** `SlixmppComponentWire` регистрирует обработчик сообщений, но не presence-событий; общего аналога `handle_xmpp_presence()` нет.

**Последствие.** Клиент может показывать запрос подписки для виртуального контакта. После удаления пользователем контакта следующая синхронизация может пропустить восстановление из-за сохранённой подписи.

**Код:** новый `xmpp_transport/adapters/xmpp/component.py:181`; старый `xmpp_transport_max/xmpp/component.py:75`, `xmpp_transport_max/core/transport.py:253`.

**Проверка:** `subscribe` и `unsubscribe` для `chat-<id>@max…`, затем повторная синхронизация контакта.

## 8. Не удаляется прежний ростерный контакт группы — средний риск

**Старое поведение.** После успешной синхронизации полноценной Xabber-группы `_remove_group_fallback_contact()` удалял старый контакт `chat-<group_id>@max…` и его подпись.

**Новое поведение.** `XmppGroupManager.ensure_group()` не выполняет такую очистку.

**Последствие.** Старые fallback-контакты, а также ошибочно созданные контакты из пункта 1 могут остаться в ростере рядом с группой.

**Код:** новый `xmpp_transport/adapters/xmpp/groups.py:44`; старый `xmpp_transport_max/core/transport.py:636`, `xmpp_transport_max/core/transport.py:716`.

**Проверка:** иметь старый `chat-<group_id>` в ростере, синхронизировать группу и проверить удаление контакта.

## Дополнительные отличия для проверки

- Старый `/login` повторно использовал сохранённый `device_id` при переавторизации. Новый `MaxBackendPlugin.create_authentication()` всегда создаёт `MaxQrAuthorizationFlow()` без прежнего ID. Это меняет идентичность web-устройства при каждом входе. Код: новый `xmpp_transport/adapters/backends/max/plugin.py:725`; старый `xmpp_transport_max/core/session_manager.py:186`.
- Старый транспорт обеспечивал наличие прямого контакта в ростере перед доставкой входящего сообщения. Новый `_receive_message()` для прямого чата публикует только `MessageReceived` и полагается на отдельное событие метаданных/snapshot. Если оно отсутствует или завершилось ошибкой, Xabber может показать неизвестный JID. Код: новый `xmpp_transport/adapters/backends/max/plugin.py:370`; старый `xmpp_transport_max/core/transport.py:175`.
- Для входящих прямых ответов старый код строил расширенную ссылку на исходное сообщение из кэша или inline MAX link, включая тело и отправителя. Новый код передаёт только `reply_to_message_id`; базовый `urn:xmpp:reply:0` остаётся, но цитата и расширенная Xabber-ссылка могут пропасть. Код: новый `xmpp_transport/adapters/backends/max/plugin.py:408`, `xmpp_transport/adapters/xmpp/gateway.py:344`; старый `xmpp_transport_max/core/transport.py:1059`.
